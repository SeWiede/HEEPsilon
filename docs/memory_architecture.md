# HEEPsilon Memory Architecture

HEEPsilon is an MCU-class platform. All memory is on-chip SRAM — there is no external DRAM interface and none is needed. This document explains the full address space, what "memory banks" means, the bus topology, and what the memory looks like on each build target.

---

## What Are Memory Banks?

The CPU SRAM is split into multiple independent 32KB blocks called banks. From software they appear as one flat contiguous address space — the split is invisible to the linker and to code. Banks exist for two reasons:

**Power gating.** Each bank has its own power switch. If your application only needs 64KB you can shut off banks 2–5, saving static leakage power. This matters on real silicon and on FPGA where every mW counts. The `POWER_MANAGER` peripheral controls which banks are on.

**Parallel access (NtoM bus).** With the default `onetoM` bus a single master (the CPU) accesses one bank at a time. With an `NtoM` crossbar and interleaved banks, multiple masters (CPU fetch, CPU data, DMA) can hit different banks simultaneously without stalling each other. This requires a different `X_HEEP_CFG` (see `example_interleaved.hjson`) and is not used by HEEPsilon's CGRA apps.

### How Many Banks Do You Need?

| Application class | `MEMORY_BANKS` | Total CPU RAM |
|---|---|---|
| Bare X-HEEP, no CGRA | 2 (default) | 64KB |
| All standard CGRA apps | 6 | 192KB |
| `transformer`, `mmul_os` | 12 | 384KB |

If the linker reports `region ram1 overflowed`, increase `MEMORY_BANKS` and re-run `mcu-gen`:

```bash
make mcu-gen MEMORY_BANKS=6
make run-verilator PROJECT=<app> MEMORY_BANKS=6
```

`mcu-gen` regenerates the linker script and the simulated hardware RAM size. Both must use the same value.

## Bus Topology

```
         CV32E40P
      instr │  data
      fetch │  port
            ▼
     ┌──────────────┐
     │  Main Xbar   │  ← generated by mcu-gen from X_HEEP_CFG + MEMORY_BANKS
     └┬──┬──┬──┬───┘
      │  │  │  │
      │  │  │  └── EXT slave port ──► CGRA IMEM        (0xF000_0000)
      │  │  └───── Peripheral bus ──► PLIC, GPIO, I2C  (0x3000_0000)
      │  └──────── AO Peripheral  ──► UART, DMA, CGRA regs (0x2000_0000)
      └─────────── SRAM banks     ──► Bank0..BankN     (0x0000_0000)
```

## CGRA Memory vs CPU Memory

The CGRA has **two** separate address regions, both completely independent of the CPU SRAM banks:

| Region | Address | What it is | How it is accessed |
|---|---|---|---|
| CGRA control registers | `0x2007_0000` (`CGRA_PERIPH_START_ADDRESS`) | Kernel ID, read/write pointers, perf counters | `cgra.base_addr` MMIO reads/writes |
| CGRA context memory (IMEM) | `0xF000_0000` (`CGRA_START_ADDRESS`) | Instruction bitstream + KMEM | `cgra_cmem_init()` at startup, then read-only by HW |

The CGRA IMEM banks (one per row, 128×32-bit each) are not CPU RAM — they cannot hold program data and do not count toward `MEMORY_BANKS`.

## Why Only SRAM? Do I Need External DRAM?

No. HEEPsilon is intentionally SRAM-only. It targets **edge and IoT deployments** where:

- Power budgets are in the μW–mW range — DRAM needs constant refresh and a memory controller, both expensive in power
- Workloads are small by design — sensor fusion, keyword spotting, small transformer inference; not server-scale models
- Latency must be deterministic — SRAM has fixed single-cycle access; DRAM has variable latency and refresh pauses

```
Traditional ML:   Sensor → MCU → cloud (DRAM + GPU) → result
HEEPsilon target: Sensor → HEEPsilon (CGRA inference on-chip) → result
```

If a workload genuinely does not fit in a few hundred KB of SRAM, HEEPsilon is the wrong platform for it. Use a Linux-capable SoC with DDR instead.

The Flash XIP interface (`0x4000_0000`) is the one "off-chip" option: code can be stored in external SPI flash and executed directly without loading into SRAM, freeing RAM for data buffers. This is used in the `flash_exec` linker mode (`LINKER=flash_exec`).

## What "SRAM" Means on Each Build Target

The same RTL compiles to different physical implementations:

| Target | SRAM banks become... |
|---|---|
| Verilator / QuestaSim simulation | Modelled in host PC RAM — no real silicon |
| PYNQ-Z2 / Nexys FPGA | Xilinx / AMD Block RAMs (BRAMs) — real SRAM cells in the FPGA fabric |
| ASIC tapeout | SRAM macros from the foundry PDK — hard macros placed by the layout tool |

On FPGA, BRAMs are the limiting resource alongside LUTs. Each 32KB bank consumes roughly 8×36Kb BRAMs on a Xilinx device. The PYNQ-Z2 (Zynq-7020) has 140 BRAMs total, so 6 CPU banks + 4 CGRA IMEM banks = ~52 BRAMs, well within budget.
